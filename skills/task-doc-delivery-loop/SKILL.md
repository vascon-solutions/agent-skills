# Task Doc Delivery Loop

Own delivery of one approved task doc or coherent ordered set in one repository. Preserve scope, exclusions, decisions, and existing authorization. An approved task doc satisfies discovery and design; do not start another planning or execution workflow.

## Endpoint And Scope

Default to a pushed branch and draft PR. A ready PR, narrower endpoint (local-only, commit-only, push-only), or merge requires explicit user wording; carry that wording forward without asking again. A ready PR does not authorize ongoing review monitoring. Never merge without explicit authorization. [Authorization](references/authorization.md) is the shared table for endpoint, monitoring, merge and what a repository may override.

Without a remote, with a non-GitHub remote, or without usable GitHub PR tooling, work up to verified local completion. That means implement, validate, review, and commit unless the user requested a narrower endpoint. Report the publication limitation. Complete at that narrower endpoint only when the user's instruction permits it; otherwise release the delivery as blocked with the limitation. Other-platform publication requires explicit direction.

Group docs only when they share one outcome, dependency order, release boundary, and reviewable PR. Separate independently shippable outcomes and primary repositories; coordinate already-authorized separate deliveries without inventing new scope. Consumer-owned generated or file-dependency refreshes belong to the consumer delivery.

## 1. Establish The Delivery

Read the task sources, relevant repo instructions, and Git state. Verify approval, prerequisites, target branch, existing PR/worktree identity, and intended dirty scope. Correct demonstrably stale mechanical references; ask only when missing approval or a material unresolved decision blocks safe work. Do not reopen settled decisions because a skill suggests another approval gate.

Use the current checkout when task-appropriate and safe. Use `isolated-worktree` for unrelated overlapping edits, protected-branch work without direct authorization, or concurrent mutators. Before installing in an isolated checkout, verify relative/file dependencies resolve to the intended sibling revision and build output; a lockfile alone does not prove freshness.

### Ledger Or Lightweight Mode

Choose the mode once, by the first rule that applies:

1. The current prompt's explicit wording, either way ("use the delivery ledger", "no ledger").
2. A user-level standing instruction applies only when rule 4 does not require a ledger. Inspect repository policy before applying this rule. Examples include a line in `~/.claude/CLAUDE.md` or `~/.codex/AGENTS.md`. It counts as user wording, below the current prompt.
3. An unfinished ledger for this branch means ledger mode. Run `path`; when `data.exists` is true, `show` supplies `phase` and `blocker`. Unfinished means `phase` is not `done` and no blocker `reason` starts with `abandoned:`, whether the ledger is owned, unowned or blocked. Report a `done` or abandoned ledger and continue to the remaining rules; a `done` ledger needs no abandonment write.
4. A repository rule: an `AGENTS.md` line, then `.agent/delivery-policy.json` `delivery_ledger: "required" | "optional"`, with `AGENTS.md` winning. `required` is a floor that only the current prompt's explicit wording overrides, never a standing user instruction; record that override as a limitation.
5. Otherwise, lightweight mode.

Never enable the ledger from risk signals alone. A required repository policy or an unfinished ledger can also select ledger mode under the rules above. When you see multi-session work, a requested phase split, an expected handoff to another runtime, or concurrent sessions on one branch, recommend it in one line.

**Ledger mode.** Keep the delivery in a [delivery ledger](references/delivery-ledger.md) through its helper, `scripts/delivery-ledger.mjs`, never by editing its JSON. Use the [worked examples](references/delivery-examples.md) for first use, a resume, or a findings batch. The owner handles this bookkeeping; the user can ask to deliver or continue without supplying JSON, hashes, revisions or claim IDs. When the user says "no ledger" while an unfinished one exists, [abandon it](references/delivery-ledger.md#abandoning-a-ledger) as a recorded state change before the ledger-free session changes the branch. Steps below marked "in ledger mode" apply only here.

**Lightweight mode** keeps the same gates as owner rules, without the helper:

- **Record.** A plain `## Delivery summary` section in the PR body, with no `agent-delivery-*` markers, or the completion report when there is no PR. It holds the endpoint and its authorization in the user's quoted wording; the spec-check verdict for feature-grade docs; validation commands, results and the tested commit; the review bound and effective delegate limit; the independent review and its finding dispositions, recorded before publishing; the verdict for each required audit mode; the defect-shape sweep; dispatch and fallback records; the push and PR read-back; and limitations. Measure a committed candidate's bound with `git diff --numstat -z --no-renames <merge-base of the verified target base and the candidate> <candidate> --`, the helper's `measure` invocation, so a rename counts as two files in both modes; local-only work states "unmeasured".
- **Owner rules.** A required independent review that is unavailable blocks, and self-review is only supplementary. Pending findings and `FAIL` or `BLOCKED` audits block completion, and no completion is claimed without a cited `PASS` for each required audit mode. Revalidate when hooks change tested inputs. Read back every push and PR write. Reply once per thread; after an uncertain read-back, inspect the remote instead of replying again. One owner per branch: a second session does not change the branch without the user's word that the first has stopped.
- **Stated limitation.** Every lightweight summary lists the guarantees it does not enforce mechanically: lock and claim, prepared-event idempotency, source-change review invalidation, candidate-bound evidence checks, the non-waivable audit gate, the push-time sweep refusal, and fresh-session resume.
- **Session.** The delivery stays in one session. On interruption, give a continuation brief built from the PR summary and Git state, or recommend switching to ledger mode, which adopts the existing branch or PR at bootstrap.

### Bootstrap

In ledger mode, after resolving the task, checkout, target base and endpoint, use `prepare-init` to generate the input files and source hashes. Fill the existing decisions, authority, dependency identities and audit policy, then `init` and `claim`. If this branch already has a ledger, validate and resume it instead. One claim covers the whole owner session: nested remediation, audit and review coordination, and publication all use it, and never claim again. In lightweight mode, the same decisions go in the delivery summary. Generated defaults are not evidence: carry a supplied spec check and requested audit forward. For feature-grade task docs, run `review-task-docs` in spec-correctness mode before implementation unless a current accepted check is supplied or the user explicitly skips it; return `revise`/`split`/`rewrite` to the authorized doc author and recheck corrected claims before delivery. For optional small-fix checks or an explicit skip, record `not_run` or `skipped` with its reason, and `not_requested` for an unrequested audit. A runtime acceptance checkpoint in the approved task doc is a requested audit: in ledger mode, bootstrap records `audit_policy` as `{required: true, state: pending, reason: <checkpoint reference>}`; in lightweight mode, the summary names the checkpoint and its required modes. [Orchestration](references/orchestration.md#audits-a-task-doc-requires) defines the trigger, the per-mode coverage the owner enforces, and why an unobservable checkpoint blocks the delivery. Read current scoped instructions and any relevant fact the phase needs. Use an existing matching goal when present; create goal tooling only when explicitly requested. Do not require a new durable plan or intermediate commits for routine work.

For migrations, auth/permissions, broad refactors, or dependent phases, record order, prerequisites, irreversible boundaries, and recovery/validation checkpoints. Write a separate plan only when the sequencing needs a durable handoff or the user requests it. Do not prewrite the implementation as a second code document.

Record a provisional review-size estimate at bootstrap (in ledger mode, in `sources.decisions`); a zero diff does not permanently make a feature small. Record the delegate-limit decision with it: unless a repository rule or user wording names a number, `delegated_limit` is `null` and delegated reviews are bounded by the size cycles alone ([review policy](references/review-policy.md)). Immediately before the first implementation review, commit the candidate (in ledger mode, `freeze` it) and finalize the bound with the size/workspace evidence described in [review policy](references/review-policy.md): in ledger mode, `measure` against the recorded `diff_base_oid` and use `set-review-bound`; in lightweight mode, measure as the summary rule above says. Recalculate for every replacement candidate before dispatch. Local-only work stays uncommitted; record the estimate and enforce the same policy inline with an explicit unmeasured limitation.

## 2. Implement And Validate

Use one implementation owner by default. Choose support work with [orchestration](references/orchestration.md): reuse applicable evidence, satisfy required independence, delegate optional read-only support only for a concrete benefit, and otherwise work directly. Installed roles do not call for dispatches; small reads and ordinary validation commands stay with the owner. Do not require a fresh implementer and two reviewers for every small step. Resolve explicit model and effort choices independently before any dispatch; otherwise use the role defaults and scale review depth to risk. Record each dispatch, direct choice and actual fallback as orchestration describes; a direct choice is never `role_unavailable`.

Read [validation](references/validation.md) when choosing checks or reusing evidence. Implement in dependency order with focused checks during development and one deduplicated required final gate. In ledger mode, generate the content manifest with `content-manifest --output-file`; the helper enumerates changed paths and computes modes, hashes and the content identity. Supply relevant input identities and explicit exclusions backed by scope decisions. Record each check with the identity it tested: the manifest for working or local-only content, the frozen OID for a committed gate. In lightweight mode, record the command, result and tested commit, or the changed paths for uncommitted content, in the summary. For local-only work, never create a commit to give the ledger an OID. Capture failing behavior before a bug fix when practical; add durable tests for named behavioral or contract risks, not for incidental copy, CSS, or DOM shape. Runtime UI acceptance may require browser inspection without requiring a permanent browser test.

Delegate a requested browser (`audit-ui`) or API (`audit-api`) audit, including one a task doc requires, with substantial observations to the canonical `auditor` role in its `ui`, `api` or `a11y` mode when the runtime offers it. It does not use up the repository's delegated implementation-review allowance. Run it on a cheaper model only when no explicit model or effort choice from the user or repository is in force. Implementation and fixes stay with the delivery owner. Before delegating, prove which URL serves the candidate. Hand over a brief with URLs, available test personas and secure credential sources, fixture identifiers and scenarios, so the auditor does not rediscover them. Consume its verdict, findings and report path, not its transcript, and send rechecks for affected checkpoints only. If the runtime cannot select the role, perform the audit inline and record that limitation (in ledger mode, `role_runs` with `execution: inline` and its `fallback_reason`). Auditing directly by choice is also allowed; either way the audit leaves a record, in the ledger's `audits` or the delivery summary. A failing audit stays failing until fixed and rechecked.

When changed behavior needs live acceptance, derive UI/API checkpoints from the task and prove the candidate source served at the selected URLs. Reuse a matching supplied environment. Otherwise, when agent-devbox is available and supports the repository, use [docker-app-verify](../docker-app-verify/SKILL.md) for environment lifecycle and hand off the selected audits with one evidence directory. An absent runner, an unsupported project, or a configured project where no supported component can serve the candidate retains its established validation path unless Docker was explicitly required; the last case records a limitation, decided before any start ([lifecycle](../docker-app-verify/references/lifecycle.md#before-starting)). The auditor does not depend on devbox: serve the candidate on the established path and hand over that proven URL. A selected configured run's guard or readiness failure remains a blocker. Executor limits leave required checks unverified; schema readiness alone is not feature acceptance. Auditors close their sessions/leases; the lifecycle owner stops only created environments and preserves borrowed services.

When a check fails, read [debugging](references/debugging.md), investigate, and fix related failures within the authorized scope. A recoverable failure is work to do, not automatically a user approval gate. Record unrelated/environmental failures and their effect on completion.

## 3. Review And Remediate

Use `review-implementation` in delivery-review mode with the task sources, complete diff, candidate identity, prior decisions, and validation evidence. Use one independent reviewer, normally the canonical `reviewer` in `implementation` mode, when requested or required and available; reuse a valid independent assessment of the same content instead of commissioning another. Otherwise perform a local review and identify its limits. When an independent review is required and no approved independent reviewer is available, report the gate as blocked (in ledger mode, a `role_runs` record with `fallback_reason: independence_required`); a self-review is only ever supplementary. Additional task-boundary reviews need an explicit gate or a material risk boundary. A PR-bound delivery receives review unless the user explicitly waives it and repo policy permits that.

Use `address-review-findings` to evaluate valid, invalid, unclear, and out-of-scope findings. Apply valid fixes as one coherent batch. Rerun invalidated checks and complete the [defect-shape sweep](../review-implementation/references/risk-classes.md). An additional focused assessment after material remediation consumes a cycle and is allowed only within the effective bound and delegate limit; local verification consumes none. Where the effective cycle bound and delegate limit permit another delegated review (a `null` limit means size cycles only), use a fresh reviewer with the remediation diff, original findings, claimed dispositions, affected requirements and candidate identity. Otherwise verify remediation locally and state the independence limit. Record review dispositions before publishing, in the ledger or the delivery summary. At the effective bound, stop ungranted cycles and report unresolved blockers; even critical findings need an explicit extension. A specific user request to fix one further batch supplies one extra cycle if needed: record it without asking again. It does not raise the separate delegate limit. Never publish known blockers as success. Keep independent work moving when one finding needs clarification.

## 4. Publish And Close

Use `publish-branch` for the agreed endpoint. Supply candidate identity and applicable evidence; publication must not invent another validation plan. If a validated commit is supplied, use exact-candidate mode. Otherwise commit the intended scope, account for hook changes, and verify the resulting candidate before pushing. For a commit, push or PR endpoint, in ledger mode `freeze` the final intended commit after hooks; in either mode, publish that candidate unchanged. Cite the original precommit review and audit records when their manifests still match the frozen content; a commit alone does not require another review or audit. In ledger mode, hand `publish-branch` the ledger under your claim; it records each push and PR write as a prepared, then verified, publication, and never runs a guarded Git or GitHub write after a failed helper call. Keep this delivery's summary block, or the lightweight `## Delivery summary` section, in the PR body.

Take one final PR snapshot: URL, base, draft/ready state, head, checks, reviews, and unresolved threads. Pending CI or reviewer approval is external state: report it accurately without calling the PR merge-ready. For a create-PR endpoint, report delivery complete with pending external checks clearly separated; keep any explicitly requested green-CI, approval, or merge gate open until satisfied. Do not wait for review or remediate newly arriving comments automatically. A separate current-findings request uses `address-review-findings`; explicit ongoing PR-review monitoring uses `monitor-pr-review`. Generic CI watching is read-only unless remediation is requested.

When monitoring was requested, consume its result once: `quiet_complete` returns to the agreed closeout gates; `waiting_for_reviewer` and `waiting_for_user` identify dependencies; `blocked` follows runtime blocking policy; `externally_terminated` requires checking closed/merged state. A quiet window or spent budget is not proof of completion.

In ledger mode, split phases into fresh sessions by default; keep one session when the user asks and record `session_mode: same_session`. At the endpoint, or on interruption when you can hand off safely, `release` the ledger with the applicable `next` (or none), and give the ledger path and a copy-ready continuation brief. Otherwise leave the claim in place. A lightweight delivery stays in one session and hands off as its session rule says. `next` is advice and authorizes nothing. Do not launch another CLI, create a task or schedule a monitor to get a fresh session, and never abandon authorized unfinished work for a cleaner context.

Report what shipped, task checkpoints, branch/commit and PR when applicable, review/finding dispositions, verification evidence and gaps, preserved unrelated files, started servers with their cleanup outcome and any residue, and remaining dependencies. Shape the report with `unslop`: outcome and gaps first, no session narration, evidence in place of adjectives, inside the completion-report budget. Reuse valid evidence instead of rerunning commands merely to write the final answer. Retrospect briefly on repeated cycles or notable delays, distinguishing measured overhead from estimates.
